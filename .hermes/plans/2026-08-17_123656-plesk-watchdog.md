# Plesk Apache Watchdog Implementation Plan

> **For Hermes:** Use this plan as the basis for implementation only after Ruben confirms execution.

**Project:** `plesk-watchdog`

**Directory:** `/home/ruben/repos/plesk-watchdog`

**Goal:** Create a small server-local watchdog for Plesk that checks the main domains one by one, appends `?health=<timestamp>` to each root URL, restarts Apache after three failures in the current complete domain-list pass, and records only restart events and the last checked domain.

**Architecture:** A Bash script runs continuously under a `systemd` service. It obtains the primary domains from Plesk, checks each domain's root URL with `?health=<timestamp>` plus cache-control request headers, waits 30 seconds between checks, and keeps one failure counter for the current complete domain-list pass. A separate installer and uninstaller make deployment reversible and repeatable.

**Tech Stack:** Bash, curl, Plesk CLI, systemd, journald, plain text log file.

---

## Functional decisions

1. The watchdog runs locally on each Plesk server.
2. The domain inventory is used exactly as returned by `plesk bin site --list`; no additional Plesk listing or filtering commands are used.
3. Domains are checked sequentially.
3. Each check targets `/` and appends `?health=<Unix timestamp>`.
4. Cache avoidance also uses request headers such as `Cache-Control: no-cache, no-store`. This prevents client/proxy reuse where honored but cannot guarantee bypass of every application, reverse-proxy, CDN, or server-side cache.
5. At the start of every complete domain-list pass, the single global failure counter is reset to zero.
6. A failed domain increments the global counter; a successful domain does not reset it.
7. When the global counter reaches three during a pass, Apache is restarted once. The counter is then reset and the next pass starts at zero.
8. There is a 30-second delay between domain checks.
9. Successes are not logged.
10. Restart logs include timestamp, reason, triggering domain, and the last domain checked.
11. The log is stored inside the project/runtime directory and must have controlled permissions and rotation/size protection.

## Important feasibility notes

- This is feasible with Bash, curl, Plesk CLI, and systemd.
- A request to `/` may be served by a static file, cache, CDN, or reverse proxy and therefore may not prove that PHP/PHP-FPM or the database is healthy. A configurable health endpoint should be supported later, even if the first version defaults to `/`.
- “No cache” cannot be guaranteed from the client side. The first version should send no-cache headers and add a cache-busting query string. The README must document this limitation.
- Plesk Obsidian documentation identifies `plesk bin site --list` as the command that displays the list of domains. Its output is used as-is, as requested.
- The target service name is fixed as `apache2`; the installer must verify that `systemctl status apache2` is available and fail safely otherwise.
- Restarting Apache after one domain reaches three failures affects every hosted site on that server. This is an intentional consequence and must be prominently documented.
- The restart command must use a lock/cooldown so multiple domains failing during one incident do not cause repeated Apache restarts.

## Implementation tasks

### Task 1: Verify the Plesk environment

- Confirm the operating system and whether Apache is `apache2` or `httpd`.
- Confirm the available Plesk CLI command for enumerating primary domains.
- Capture sample output containing a normal domain, subdomain, and alias.
- Confirm whether `curl` is installed and which user/systemd permissions are appropriate.
- Define a safe test domain and a deliberately unavailable test endpoint.

### Task 2: Define configuration

Create a shell-readable configuration with defaults for:

- Plesk domain-list command.
- Apache service name.
- Check URL path, default `/`.
- Request timeout and connection timeout.
- Failure threshold, default `3`.
- Delay between checks, default `30` seconds.
- Restart cooldown.
- Runtime state directory.
- Log path.
- Optional curl arguments and user-agent.

The configuration must validate numeric values and paths before the watchdog starts.

### Task 3: Implement domain discovery

- Invoke `plesk bin site --list`, as documented for Plesk Obsidian's `site` utility.
- Normalize whitespace and remove empty lines.
- Verify the output format on the target server before relying on a column position.
- Use the `site --list` result as-is; do not call separate subdomain or alias commands.
- Reject malformed hostnames.
- Deduplicate domains.
- Exit safely with a clear error when no primary domains are found.

### Task 4: Implement one-domain health checks

- Build `https://domain/` or the Plesk-configured scheme.
- Send cache-control request headers.
- Add `?health=<Unix timestamp>` without changing the configured application path. If the root URL already has a query string, append with `&health=...`.
- Use bounded connection and total request timeouts.
- Treat only an accepted HTTP response range as success; define the range in configuration.
- Do not log successful requests.

### Task 5: Implement counters and restart protection

- Reset one global failure counter at the beginning of each complete domain-list pass.
- Increment that global counter for each failed domain; successful domains do not reset it.
- When the global counter reaches three, verify the current Apache state and restart `apache2` through `systemctl`.
- Restart at most once during a pass, then reset the counter and begin the next pass normally.
- Prevent concurrent watchdog instances with a lock.
- Add a restart cooldown to avoid restart storms.
- After restart, wait for Apache to become active and perform a bounded verification.
- Log only restart attempts/results, timestamp, triggering domain, failure count, and last domain checked.

### Task 6: Implement systemd integration

- Create a long-running service with automatic restart on unexpected exit.
- Run with least privilege compatible with Plesk CLI and Apache restart permissions.
- Use a narrowly scoped `sudoers` rule if a non-root user is possible; otherwise document why root is required.
- Set suitable `After=` and `Wants=` dependencies.
- Ensure stop/restart operations are clean.
- Prevent duplicate instances.

### Task 7: Create installer and uninstaller

Installer requirements:

- Check root privileges and required commands.
- Detect or request Apache service name.
- Install files and configuration with safe permissions.
- Create runtime/log directories.
- Run `systemctl daemon-reload`.
- Enable and start the service.
- Verify service state and show the installed paths.
- Be idempotent.

Uninstaller requirements:

- Stop and disable the service.
- Remove the unit and installed executable/configuration.
- Preserve logs by default, or require an explicit purge option.
- Run `systemctl daemon-reload`.
- Report remaining preserved files.

### Task 8: Write README.md

Document:

- Purpose and architecture.
- Supported assumptions and Plesk prerequisites.
- Installation and uninstallation commands.
- Configuration options.
- How domains are selected.
- Exact meaning of a failure and success.
- Cache-bypass limitation.
- Why restarting Apache affects all sites.
- Log format and location.
- How to inspect status and logs with `systemctl` and `journalctl`.
- Manual test procedure.
- Rollback procedure.
- Troubleshooting.
- Security and permissions.

### Task 9: Test and validate

Use shell-level tests with mocked `plesk`, `curl`, and `systemctl` commands. Cover:

- Empty domain list.
- Primary domain filtering.
- Site-list-only domain discovery.
- A new complete domain-list pass resetting the global counter.
- One and two failed domains in a pass without restart.
- The third failed domain in a pass causing one restart.
- Successful domains not resetting the global counter during that pass.
- Multiple failing domains not causing a restart storm.
- Curl timeout and DNS failure.
- Apache restart failure.
- Lock contention.
- Installer idempotency.
- Uninstaller preserving logs.

On a real non-critical Plesk server, verify:

1. The discovered list is correct.
2. No success lines are written to the log.
3. A controlled failure reaches the threshold.
4. Apache restarts exactly once.
5. Apache returns to active state.
6. The log contains the restart timestamp, triggering domain, and last checked domain.
7. `systemctl status` and `journalctl` show the expected service behavior.

## Acceptance criteria

- The service starts automatically after reboot.
- It checks all primary domains sequentially.
- It waits 30 seconds between checks, configurable without code changes.
- It does not log successful checks.
- It restarts Apache when the third domain failure occurs within the current list pass.
- It does not repeatedly restart Apache during one outage.
- Restart records include timestamp and last checked domain.
- Installer and uninstaller work repeatedly without corrupting the installation.
- README instructions are sufficient for a fresh administrator to install, inspect, test, and remove it.
- The real-server test confirms the domain filtering and restart behavior.

## Open decisions before implementation

1. The check should use HTTPS with `curl -L`; redirects are valid and the final response should be evaluated.
2. HTTP 3xx responses should be accepted when the redirect chain ends in the configured success range.
3. The global failure counter should remain in memory; a process restart begins a new list pass at zero.
4. Should the log live in the project directory, or in `/var/log/plesk-watchdog/` with the project path used only for source files? The latter is more conventional for a system service.
5. Should a failed restart trigger Telegram/email notification immediately, or only be visible in journald/log files?
6. What Plesk version is used on the first target server? The documented command located is `plesk bin site --list` in the Plesk Obsidian `site` CLI documentation: https://docs.plesk.com/en-US/obsidian/cli-linux/using-command-line-utilities/site-sites.67067/

## Recommended first implementation scope

Implement only one local Bash daemon, one systemd unit, configuration, installer, uninstaller, README, and mocked tests. Do not add a central monitor, Ansible deployment, database checks, or automatic server discovery until the local behavior is verified on one non-critical Plesk server.
